# 样本库 sample_bank v0.1

> 用途：把产品每天**看到什么、选了什么、为什么打回、后来涨没涨**存成可复算的面板，供迭代找新 alpha。
> 边界：**只读** `product/reports/` 下的产物，不改产品本体、不写产品目录。
> 建立：2026-11-08。当前库 `sample_bank.db`：10 个 run / 504 条样本 / 131 只代码 / 92 条智能体意见。

## 一、为什么不是「日志」

只存日志只能回看，不能研究。要能找 alpha，样本必须同时满足四条：

1. **有决策时点**：每条记录都必须是 D 日收盘前能看见的字段，不许用 D+1 的信息补。
2. **有反例**：只存选中的票，学到的是「它喜欢什么」，不是「什么会涨」。漏斗里被刷掉的票必须一起存。
3. **有结果**：T+1 开盘 → T+1/T+5/T+10/T+20/T+60 的收益与超额，缺失记状态不填 0。
4. **有版本**：同一条规则的不同版本要分开（v1.3 的 119 只和 v1.5 的 80 只不是同一队列）。

## 二、库结构（SQLite）

| 表 | 一行是什么 | 关键字段 |
|---|---|---|
| `runs` | 一次运行 | run_id、日期、时段、模式、版本、大盘定档、漏斗、委员会计数、源目录、源文件 hash |
| `samples` | 一个 (run, 股票) | 代码/名称/赛道/决胜分/分类/五格/现价/涨跌/VWAP 偏离/止损距离/盈亏比/前波涨幅/回调量/成交额/委员会判定/轮次/依据 |
| `labels` | 上面那行的结果 | 入场日、ret1/5/10/20/60、ex5/ex20（对沪深300）、flag（一字/停牌）、数据源 |
| `daily_memory` | 一个交易日 | 大盘定档、漏斗、委员会结论、池子数、通过数、打回数 |
| `agent_notes` | 一条多/空/审意见 | run、代码、speaker（多/空/审）、原文 |

## 三、怎么跑

```bash
python sample_bank/bank.py init      # 建库
python sample_bank/bank.py ingest    # 扫 reports/，幂等
python sample_bank/bank.py label     # 补收益（腾讯前复权，带缓存）
python sample_bank/bank.py report    # 一页统计
```

## 四、当前实测（2026-11-08 首跑）

- 10 个 run、504 条样本、131 只代码、92 条智能体意见；全部 504 条都打上了标签。
- **只有 3 个独立交易日**：10-22（119 只，v1.3 全 LLM 委员会）、11-02（15 只）、11-04（80 只）。
- 按日去重后的分数-收益关系：

| 日期 | 版本 | ret1 IC | ret5 IC | ret10 IC | 说明 |
|---|---|---|---|---|---|
| 10-22 | v1.3 | −0.270 | **+0.287** | +0.193 | 单截面 n=119，5 日正、1 日负 |
| 11-02 | v1.5 | +0.305 | — | — | n=15，窗口未到 |
| 11-04 | v1.5 | +0.036 | — | — | n=80，窗口未到 |

**这些数不能当结论**：每个日期只有一个截面，n=1 的 IC 是日效应不是因子效应；10-22 还是旧版本。它们的用处是证明管道通了、并给出第一组可追问的现象（同一天 1 日 IC 与 5 日 IC 符号相反）。

- 智能体意见的词频已经能出东西：空方第一高频理由是「大盘不在进攻期」（20 次），第二是「买价离分时均价太远」（VWAP 偏离，多次）。这两条是**系统自己的否决器在说话**，比任何外部研报都值得先修。

## 五、它现在**没有**覆盖什么（最重要的一条）

`pool.csv` 只含进入「精算」的票。漏斗 `板块 300 → 达标 120 → 精算 119` 里，**被「达标」刷掉的 180 只不在库里**。所以：

- 现在能回答「进入精算的票里，分数高的后来涨得好吗」；
- 不能回答「没进精算的票里，有没有被误杀的 alpha」。

补法两条，按代价排序：
1. **研究侧重算**（不动产品）：用 `product/tools/audit_product_score.py` 的做法，在 D 日对全市场重算评分，把没进池的票也落成样本。已有 121 天 × 438 只的先例。
2. **产品落盘漏斗明细**（要改产品，需任务板立项 + 发版）：`summary.txt` 已有漏斗计数，但没有名单。

## 六、四条防自欺规则

1. **run ≠ 样本**：同一天多次扫描是同一个截面，统计必须按 (日期, 代码) 去重，只取当天最后一次 run。库里保留了全部 run，但 `report` 的去重表才是可用于统计的口径。
2. **只追加，不覆盖**：`runs.src_sha` 记源文件 hash；重跑 ingest 是幂等替换，不会改历史数值。label 表只增不改。
3. **结果与决策分表**：`samples` 只放当时可见的字段，`labels` 事后追加；任何时候都不许把结果回填进决策表。
4. **缺失不填 0**：停牌、一字板、窗口未到都记 `flag` 或 NULL，不补零。

## 七、下一步（按顺序）

1. **每天收盘后自动 ingest + label**（已落地）：用系统计划任务在周一至周五收盘后跑一个批处理脚本，日志落本地 `logs/`。注意：bat 必须写成 **纯 ASCII + CRLF**，写中文注释或 UTF-8 换行会被 GBK 控制台读坏（实测会把 `cd /d` 那行整个吃掉）。
2. 把 `agent_notes` 做成否决器词表：统计每类理由的触发率与后续收益，回答「哪条否决器在赚钱、哪条在赔钱」。
3. 全截面补齐（研究侧重算），把「没进池的票」也变成样本。
4. 版本 cohort：v1.3 与 v1.5 在同一批日期上的 IC 差，是「迭代有没有用」的唯一硬证据。
5. 版本 cohort 攒够 6 个月后，再谈 alpha 衰减率（半衰期）与「每季度要补多少新 alpha」——先有样本，再有补偿公式。
